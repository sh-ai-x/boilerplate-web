## §1 Frame

- **goal**: Ship `npx create-boilerplate-web <folder> --type=<saas|shop|portfolio>` as a published npm package with OIDC trusted publishing, so users can scaffold from any directory without cloning the repo first.
- **target user**: Solo indie hacker (extends 0-mvp persona) — runs `npx create-... my-saas --type=saas` from their home directory, not from a cloned boilerplate-web checkout.
- **situation**: Today the CLI only works via `node cli/index.js` inside a clone of boilerplate-web. Users have to git-clone the full repo (including templates + Edge Functions + tests) just to scaffold a new project.

## §3 Non-goals

| # | Non-goal | Rationale | Breach-response |
|---|----------|-----------|-----------------|
| 1 | **No non-npm install path** (no JSR, no direct curl, no Homebrew). | OIDC trusted publishing + npm provenance covers the security story; adding install paths multiplies the release surface. | If reviewer asks for curl install → open a `feat(install-alternatives)` PRD, do NOT add scripts to this phase. |
| 2 | **No multi-template bundle** (one `--type` per scaffold; users run `npx` twice for two templates). | Templates are independent Next.js apps with separate deps and deploy targets; bundling them risks pulling in Edge Functions + Cloudflare config the user did not ask for. | If reviewer asks for one-shot multi-template → open `feat(multi-scaffold)`, do NOT graft into this phase. |
| 3 | **No auto-update / self-update mechanism.** | npm's own update flow (`npm create ...@latest` or version tag) is the canonical channel; a custom updater duplicates it. | If reviewer asks for self-update → defer to npm-native; do NOT add a side-channel updater. |
